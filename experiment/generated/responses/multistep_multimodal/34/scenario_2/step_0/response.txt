When assessing the security of an admissions system, auditors typically evaluate several areas where vulnerabilities commonly occur.

### Authentication and Authorization
Admissions systems handle sensitive personal and financial data, making robust access controls critical.

*   **Insecure Direct Object References (IDOR):** This occurs when an application provides direct access to objects based on user-supplied input. In an admissions context, an IDOR vulnerability might allow an applicant to view or modify another applicant's data by manipulating a parameter, such as an application ID in a URL.
*   **Broken Authentication:** Weak session management, lack of multi-factor authentication (MFA), or predictable session tokens can lead to account takeover.
*   **Privilege Escalation:** Flaws in authorization logic might allow a standard user (e.g., an applicant) to access administrative functions, potentially allowing them to alter application statuses or access bulk data.

### Injection Vulnerabilities
Admissions processes often involve extensive data entry through web forms. If this input is not properly validated and sanitized, the system may be vulnerable to injection attacks.

*   **SQL Injection (SQLi):** If user input is concatenated directly into database queries, an attacker could manipulate the query to extract sensitive data, modify records, or bypass authentication. Security audits verify the use of parameterized queries or Object-Relational Mapping (ORM) frameworks to prevent SQLi.
*   **Cross-Site Scripting (XSS):** If the system displays user-supplied data (such as an essay or personal statement) without proper encoding, an attacker could inject malicious scripts. These scripts could execute in the browsers of administrators reviewing the applications, potentially leading to session hijacking or unauthorized actions performed on behalf of the administrator.

### Insecure File Uploads
Applicants are frequently required to upload supporting documents like transcripts or portfolios.

*   **Malicious File Execution:** If the system does not adequately restrict the types of files that can be uploaded or fails to store them securely, an attacker might upload an executable file (like a web shell). If the server executes this file, it can lead to full system compromise. Audits check for strict file type validation (using magic numbers, not just extensions), the use of isolated storage environments, and the renaming of uploaded files.

### Business Logic Flaws
These vulnerabilities involve flaws in the design and implementation of the application's intended workflow.

*   **Workflow Bypass:** An attacker might manipulate the sequence of steps in the admissions process. For example, they might find a way to skip a required payment step or move an application to a "submitted" or "approved" state without fulfilling all prerequisites. Audits involve thorough testing of the application's state machine to ensure transitions are strictly enforced.
